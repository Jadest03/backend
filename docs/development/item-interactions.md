# 일정 항목 좋아요·댓글 내부 구현

## 범위와 근거

BE2 저장 구조와 내부 처리 로직이다. 컨트롤러와 실제 권한 어댑터는 아직 없다.
서비스도 컴포넌트 스캔으로 등록하지 않는다. 실제 권한 검사가 없는 채로 API가 열리지 않게 한다.
인기 코스 데이터에 붙는 기능이 아니라 사용자의 여행 일정 항목에 붙는다.

- 인수인계 문서 8장: `(tripId, itemId)`에 연결하며 일정 버전과 무관하게 유지한다.
- 항목이 일정에서 빠져도 기록은 지우지 않고 현재 조회에서만 숨긴다.
- 노션 개인 복사본의 5개 명세를 2026-11-10에 읽었다. 본문은 모두 비어 있으며 경로·메서드·일부 메모만 있다.
  - [좋아요](https://www.notion.so/76eeeb44a8de8315add40171935d4120): `POST /api/trips/{tripId}/items/{itemId}/likes`
  - [취소](https://www.notion.so/c47eeb44a8de836cabf38137fb71d8c1): 같은 경로 `DELETE`
  - [댓글 작성](https://www.notion.so/82feeb44a8de8359824c01f9884d6879): `POST /api/trips/{tripId}/items/{itemId}/comments`
  - [댓글 목록](https://www.notion.so/69deeb44a8de8363992481791616abbb): `GET /api/trips/{tripId}/comments`
  - [댓글 삭제](https://www.notion.so/3e4eeb44a8de824aa1d0814344e73136): `DELETE /api/comments/{commentId}`. 메모: 삭제된 장소의 댓글은 이력에 보관.

위 주소는 연결할 예정인 명세이며 이번 변경에서 HTTP API로 제공하지 않는다.

## 저장과 처리

- `item_likes`: 여행 FK, 항목 ID, 사용자 FK, 생성·수정 시각. `(trip_id,item_id,user_id)` 유일 제약.
- `item_comments`: 여행 FK, 항목 ID, 작성자 FK, 본문, 생성·수정 시각. 여행·항목·시각·ID 인덱스.
- 일정 버전이나 Google placeId를 키로 쓰지 않는다. 항목 ID는 대소문자를 구분한다.
- `like`/`unlike`: 반복 호출 가능. 다른 사람의 좋아요는 유지한다. 현재 개수와 내 좋아요 여부 반환.
- `addComment`: 빈 글을 거절하고 입력 본문을 그대로 저장한다. 기획상의 글자 수 제한은 미정이다.
  현재는 MySQL TEXT 저장 한도인 UTF-8 65,535바이트 초과를 입력 오류로 거절한다.
- `listComments`: 여행의 최신 항목 ID에 붙은 댓글만 작성 시각·ID 오름차순으로 반환한다.
  작성자 ID·이름·사진 URL과 작성 시각을 반환하며 이메일·인증 정보는 포함하지 않는다.
- `deleteComment`: 작성자만 삭제 가능. 여행 소유자도 남의 댓글은 삭제하지 못한다.
  없는 댓글·남의 댓글은 `COMMENT_NOT_FOUND`로 처리한다.
- 빠진 항목은 쓰기·삭제에서 `ITEM_NOT_FOUND`. 기록은 보존하며 같은 ID가 돌아오면 다시 조회된다.
  이는 현재 내부 구현의 정책이며 이력 화면에서 별도로 댓글 삭제를 제공할지는 미정이다.
- 모든 쓰기는 여행 행의 `PESSIMISTIC_WRITE` 잠금 안에서 처리하여 좋아요 중복 요청을 직렬화한다.
  DB 유일 제약도 중복 행을 차단한다. 이 잠금은 같은 여행의 다른 항목 쓰기도 직렬화하는 단순한 방식이다.

## BE1 연결 후 할 일

`InteractionAccess.activeItemIds(userId, tripId)`의 실제 구현이 필요하다.
다음 사항을 확인하는 어댑터를 구현한 후 서비스를 명시적으로 빈 등록하고 위 명세의 컨트롤러를 연결한다.

1. 로그인 사용자가 여행 소유자 또는 수락된 동행자인지 확인. 초대 대기·탈퇴·공유 링크 열람은 제외.
2. 없는 여행·권한 없음은 `TRIP_NOT_FOUND`. 최신 저장 일정의 실제 항목 ID 집합만 반환.
3. 일정 수정·동행 변경 쪽도 같은 여행 행 잠금 또는 동등한 동시성 보장을 사용하도록 연결 검토.
4. 실 데이터로 일정 버전 변경, 항목 제거·복원, 초대 수락·탈퇴를 검증.
5. HTTP 요청·응답 계약, 댓글 길이·정렬·페이지 처리 등 공개 정책을 확정하고 실제 HTTP 검증.

테스트의 `TestAccess`는 테스트 전용 메모리 대역이다. 실제 초대·일정 저장 연동을 검증한 결과로 해석하면 안 된다.
기존 Trip/User/BE3 일정 로직은 수정하지 않는다. 서버 환경변수와 외부 API 호출은 추가하지 않는다.

## 이번 검증

- `bash gradlew clean build --no-daemon`: 실제 MySQL 8.4 사용, 전체 277개 통과, 실패·건너뜀 0개.
- 새 테스트 26개: DB 유일 제약, 접근 거절, 작성자 삭제, 여행 분리, 항목 제거·복원, 본문 바이트 경계 등.
- 동시 요청 108건: 동일 사용자 좋아요·취소 반복, 두 사용자 좋아요, 동시 댓글, 좋아요·취소 혼합.
- 실제 로컬 서버: health UP, 기존 여행 생성 201·조회 200, 연결 전인 댓글 목록·좋아요·댓글 작성 주소 404 확인.
- 권한과 최신 항목은 테스트 대역으로만 검증했다. 실제 BE1 초대·일정 저장 연동과 HTTP 계약 검증은 남아 있다.
